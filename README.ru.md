# rag-mbti — RAG-справочник по соционике

[English](README.md) · **Русский**

Учебно-исследовательский проект: RAG-система поверх корпуса из 16 соционических
типов, MCP-сервер и свой агентный цикл на Python и TypeScript. Основной интерес
не в самом боте, а в **методике измерения** — ретривала, генерации и поведения
агента: каждое изменение проверено замером, а не ощущением.

## Результат

| Метрика ретривала | Baseline | Итог | Прирост |
|---|---|---|---|
| Recall@3 | 0.398 | **0.932** | +134% |
| Recall@5 | 0.670 | **1.000** | +49% |
| MRR | 0.383 | **0.966** | +152% |

Замер на golden set из 22 запросов, размеченных по 8 категориям.

### Что дало прирост

| Изменение | Стоимость | Вклад в Recall@3 |
|---|---|---|
| BM25 + гибридное слияние | бесплатно | +0.295 |
| Чанкинг + small-to-big | бесплатно | +0.193 |
| Смена эмбеддинг-модели на многоязычную | 1.2 ГБ + зависимость | +0.023 (шум) |
| Настройка веса слияния | бесплатно | +0.023 (шум) |
| Авто-фильтр по дихотомиям | +2-5 с на запрос | 0 при k=3, +0.045 при k=5 |

Главный вывод: **структура корпуса и выбор алгоритма поиска дали почти всё
улучшение, а смена модели на более тяжёлую — статистический шум.**

## Архитектура

```
вопрос
  │
  ├─ ретривал (retrieve.py)
  │    ├─ семантический  — векторный поиск, эмбеддинги через ollama или Chroma
  │    ├─ лексический    — BM25 со стеммером-обрезкой (lexical.py)
  │    └─ гибрид         — взвешенный Reciprocal Rank Fusion
  │         └─ small-to-big: ищем по чанкам, отдаём тип целиком
  │
  └─ генерация (rag.py -> generate.py)
       └─ провайдер-агностичная обёртка: ollama / OpenAI-совместимый API

интерфейсы:
  bot.py         — Telegram, long polling
  mcp_server.py  — MCP-сервер: справочник как инструменты для любого агента

агенты (клиенты MCP-сервера):
  agent.py           — агентный цикл на Python, ollama + qwen2.5-7b
  ts/agent_loop.ts   — тот же цикл на TypeScript, не зависит от сервера
```

### Ключевые решения

- **Гибридный поиск.** Векторный поиск плохо ловит редкие точные токены (имена,
  коды типов), BM25 — наоборот. RRF складывает не скоры (они в разных шкалах),
  а обратные позиции: `вес / (60 + место)`.
- **Вес слияния зависит от конфигурации.** На цельных документах семантику
  приходится глушить (0.3), на чанках ей полагается равный вес (1.0): короткий
  фокусный текст она понимает лучше. Веса подобраны разверткой (`sweep.py`).
- **Small-to-big.** Мелкие чанки хороши для поиска, крупные — для ответа.
  Индексируем чанки, наружу отдаём документ-родитель.
- **Metadata-фильтрация.** Структурные запросы («интуит + логик + экстраверт»)
  векторным поиском не решаются в принципе — для них точный фильтр по metadata.
- **Query understanding с привратником.** Структурные запросы разбирает LLM
  (structured output + валидация + fail-open), но перед ней стоят две
  детерминированные проверки: назван ли конкретный тип и назван ли слот
  Модели А. Замер показал, что без них LLM строит фильтры там, где они вредны,
  и роняет качество на 0.137. Не проси модель решать то, что определяется
  поиском по словарю.
- **Блокирующий вызов вне event loop.** Ответ RAG считается ~10 секунд
  синхронно. В асинхронном боте такой вызов заморозил бы обработку всех
  пользователей, поэтому он уходит в поток через `asyncio.to_thread`.
- **Валидация корпуса.** Функции Модели А выводятся из базовой и творческой
  по строгому правилу, инвариант проверяется скриптом: LLM-сгенерированные
  данные — это черновик данных, а не данные.

## Метрики

**Ретривал:** Recall@k (полнота — всё ли нашли) и MRR (ранжирование — насколько
высоко стоит правильный). Пара выбрана намеренно: Hit Rate теряет информацию,
а по отдельности они скрывают разные типы провалов.

**Генерация:** groundedness (не выдуманы ли сущности — программная проверка
вместо LLM-судьи, домен конечный), citation rate, refusal rate на вопросах,
ответа на которые в корпусе нет.

## MCP-сервер

Справочник доступен любому MCP-клиенту (Claude Code, Claude Desktop, Cursor)
как набор возможностей. Подключение уже описано в `.mcp.json`: достаточно
открыть репозиторий в Claude Code и подтвердить сервер.

| Примитив | Что | Кто решает использовать |
|---|---|---|
| tool `search_types` | гибридный поиск по вопросу свободным текстом | модель |
| tool `filter_types` | точный отбор по дихотомиям (параметры-слова, см. ниже) | модель |
| tool `get_type` | карточка по любому названию, склонениям, буквам MBTI | модель |
| resource `mbti://types/{id}` | полный текст типа | приложение |
| prompt `compare_types` | сравнение двух типов по Модели А | пользователь |

Решения:

- **Сервер отдаёт данные, а не рассуждения.** Генерации ответа нет: клиент —
  сильная модель. Разбор «интуитивный логик экстраверт» на признаки, который
  локальная 7B-модель делала с инверсиями, переезжает на клиента.
- **Текст ошибки — подсказка модели.** `get_type` на неоднозначное название
  перечисляет кандидатов вместо угадывания, на опечатку в коде MBTI
  предлагает ближайшие по буквам, на имя человека прямо запрещает определять
  тип самостоятельно.
- **Мягкая деградация.** Без ollama `search_types` отвечает через BM25 и
  помечает ответ флагом `degraded`. Цена известна из замера: recall@3 тот же,
  MRR 0.955 → 0.871. Предохранитель после сбоя 30 с не обращается к ollama.
  Ядро `retrieve` при этом падает громко, чтобы замеры не посчитались молча на
  запасном режиме.
- **Раздельные таймауты** по замеру: запрос — 3 с (медиана 106 мс, холодный
  старт 1.1 с), загрузка корпуса — 120 с (батч 144 чанков идёт 3.4 с).

`src/mcp_raw_client.py` разговаривает с сервером на голом JSON-RPC без SDK —
показывает протокол построчно.

## Генерация

Провайдер-агностичная обёртка: ollama локально или любой OpenAI-совместимый API
(смена — правка конфига). Промпт вынесен отдельно и существует в двух вариантах,
чтобы сравнивать их замером.

| Метрика | strict | loose (наивный промпт) |
|---|---|---|
| groundedness | 1.00 | 1.00 |
| citation | 0.75 | 0.00 |
| refusal на вопросах без данных | 0.83 | **0.00** |
| ложных отказов | 0.00 | 0.00 |
| сек/ответ | 11.9 | 19.6 |

Наивный промпт сочинил ответ на **все** вопросы, данных для которых в корпусе
нет: выдумал соционический тип Илона Маска, статистику «1-2% населения» со
ссылкой на «современные исследования» и несуществующего основателя соционики.

Показательно, что **groundedness этого не заметила** (1.00 у обоих): она
проверяет сущности, а сущности в выдумках были из контекста — выдумано было
само утверждение. Провал поймала только метрика отказов. Отсюда вывод: набор
метрик должен покрывать разные режимы отказа, потому что каждая отдельная
метрика слепа к чему-то.

## Агентный цикл

Агент — не особая модель, а цикл вокруг обычной: модель отвечает текстом или
просит вызвать инструмент; программа выполняет вызов, дописывает результат и
спрашивает снова — пока не будет ответа или не кончится лимит шагов.
`src/agent.py` и `ts/agent_loop.ts` — один и тот же цикл без фреймворка, клиент
нашего MCP-сервера.

Решения:

- **Текст — не команда.** Вызов, напечатанный текстом в ответе, не
  разбирается и не исполняется: иначе любая строка в контексте может
  «напечатать» вызов (prompt injection). Модель получает ограниченное число
  попыток переделать вызов, потом честный отказ.
- **Ошибки — по вопросу «кто может исправить».** Ошибку инструмента, не тот
  инструмент или битые аргументы модель видит текстом и исправляет сама. Сбой
  инфраструктуры (сервер упал, обрыв) модели не показывается: цикл
  останавливается с честным отказом. Это белый список: модели уходит только
  перечисленное, остальное — остановка. Проверено (`node agent.ts
  --infra-demo`): если отдавать модели всё подряд, на упавшем сервере она за
  24 с отвечает по памяти и ошибается, а мониторинг видит «успешный» ответ.
- **Белый список инструментов исполнителя** — проверка в коде, а не в промпте:
  имя инструмента может подсунуть текст из результата.
- **Нет прогресса — стоп.** Тот же вызов с той же ошибкой второй раз подряд
  при temperature 0 повторится и дальше: цикл останавливается (6 шагов → 2).
- **`null` в аргументах = «не задано»**: маленькие модели так пишут
  необязательные поля, а схемы серверов `null` часто не принимают.

На qwen2.5-7b — 3 из 6 контрольных вопросов, провалы трёх классов: неверный
аргумент, неполный план, вызов текстом. После переноса цикла на TypeScript
классы повторились один в один: ошибки идут от модели и того, что она видит, а
не от кода цикла.

## Дизайн инструмента: замер

На вопрос «интроверт, логик, **сенсорик**, иррационал» модель передавала
`is_intuitive=true`: boolean требует отрицания («сенсорик» = НЕ интуит).
`src/eval_tool_design.py` меряет только первый вызов модели — форму параметров
`filter_types` при одинаковом описании, 16 вопросов на всех 6 порядках
инструментов:

| Вариант | exact | перевёрнутых признаков |
|---|---|---|
| boolean (`is_intuitive: true/false`) | 7–13 из 16, среднее 10,5 | 12 |
| слова (`perception: "intuitive" \| "sensing"`) | 13–15 из 16, среднее 14,2 | 0 |

- **Скрытая переменная.** Первый замер дал 10 против 15, но boolean стоял в
  списке вторым, а enum — последним. Перестановка одного boolean двигала
  результат на 3 вопроса — поэтому замер на всех порядках.
- Enum со значениями на русском («сенсорик») не лучше английского: модель
  переписала из вопроса и отрицание («не логик»). Помогло именно отсутствие
  отрицания.
- Значение вне списка отклоняет сама схема (`Literal`) — ошибка со списком
  допустимых, а не молча расширенный фильтр (`tests/test_filter_types.py`).

**Улучшение компонента ≠ улучшение системы.** После перехода на enum прогон
агента целиком исправил целевой вопрос, но обнажил другой дефект: поиск всегда
возвращает k типов, и агент приписывает тип реальным людям
(`src/eval_people.py`: 6 из 7). Порог релевантности отвергнут встречной
проверкой до кода: расстояния нормальных и чужих запросов перекрываются, а
хороший смысловой запрос («прирождённый оратор») имеет BM25 = 0. Правка
описания инструмента не помогла и сломала соседний вопрос — откачена.
Дефект открыт.

## asyncio: замеры

| Демо | Что показывает | Итог |
|---|---|---|
| `asyncio_demo.py` | блокирующий вызов в `async def` против `to_thread`, 3 пользователя | 6 с против 2 с |
| `asyncio_limits_demo.py` | 10 платных задач, лимит сервиса 3 | `gather` без лимита: ошибки 429 и списание за брошенные задачи; смета + семафор + `TaskGroup`: 4 с, 10 из 10 |
| `checkpoint_demo.py` | падение посреди 10 оплачиваемых шагов | без checkpoint 17 оплат, с checkpoint 11: шаг, шедший в момент сбоя, — повод для ключа идемпотентности |
| `parallel_bench.py` | golden set через полный RAG на локальной ollama | клиент с параллельностью 8 — ~1,1×: узкое место — сервер; batching в ollama — ~1,2× ценой +1,4 ГБ |

## Ограничения

Честно о том, чему в этих цифрах верить не стоит:

- Golden set мал (22 запроса). Разница меньше ~0.05 неотличима от шума.
- Вес слияния подбирался без отложенной test-выборки — это переобучение под
  eval-set. Правильно: делить на dev/test заранее.
- Категория `structured` при k=3 остаётся 0.67. Авто-фильтр поднимает её до
  1.00 при k=5, но на рабочей точке k=3 выигрыша не даёт, а стоит 2-5 секунд —
  поэтому по умолчанию выключен.
- groundedness проверяет только сущности (entity-level) и слепа к выдуманным
  утверждениям (claim-level).
- Метрика отказов считает отказом ответ, который начинается с «данных нет», но
  дальше всё равно рассказывает из общих знаний.
- Корпуса отношений между типами нет.
- Замеры агента малы (6 контрольных вопросов, 16 в eval дизайна инструмента,
  одна модель): это сила эффекта на классе ошибок, а не доля в реальном трафике.

## Запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
ollama serve &
ollama pull bge-m3 && ollama pull qwen2.5:7b

.venv/bin/python src/ingest.py all          # собрать все коллекции
.venv/bin/python src/rag.py "кто такой Дон Кихот"
.venv/bin/python src/evaluate.py            # сравнить конфигурации ретривала
.venv/bin/python src/eval_generation.py     # сравнить промпты генерации
.venv/bin/python src/sweep.py bge-m3 chunked  # развертка веса слияния

# MCP: проверить сервер на голом протоколе и прогнать тесты
.venv/bin/python src/mcp_raw_client.py
.venv/bin/python -m pytest tests

# агент на Python и замеры агента
.venv/bin/python src/agent.py
.venv/bin/python src/eval_tool_design.py --orders
.venv/bin/python src/eval_people.py

# TypeScript: клиент и агент (Node 22.18+ запускает .ts без сборки)
cd ts && npm install
node mcp_client.ts && node agent.ts
npx tsc && node --test

# Telegram-бот (токен получить у @BotFather, в git не коммитить)
export TELEGRAM_BOT_TOKEN="..."
.venv/bin/python src/bot.py
```
